# Molly protected file sharing

Wire contract for the threshold file sharing between Molly clients and MihuBot ("S"), implementing the
design in the Molly workspace (`THRESHOLD_FILE_SHARING.md`). A shares a small encrypted file or text note
with B; B recovers it only with S's cooperation and approvals from M of N trustees.

All share actions travel inside the sealed `POST /api/molly` transport ([README.md](README.md)).
Test vectors: `MihuBot.Tests/Molly/FileSharingVectors.json` (generated by `FileSharingVectorsTests.cs` in the
same directory from .NET primitives, independently of the server's file sharing code).

## Conventions

- Integers are unsigned big-endian unless stated otherwise. `i64` is a signed big-endian Unix time in seconds.
- `ACI` is the 16-byte big-endian UUID of a Signal ACI. `KEY` is a 33-byte Signal identity public key
  (`0x05 || X25519 public key`); any other type byte is rejected.
- `ENTRY` is a random 16-byte entry ID chosen by S (see `share-reserve`); clients reject an all-zero one.
- `P` is the ASCII prefix `MihuBot.Molly.Share.v1/`. Labels are ASCII without a terminator.
- `SHA-512` is used for every hash, HMAC and HKDF. The only other hash is inside libsignal's HPKE suite.
- Fixed-size objects are validated by exact length; `u16`/`u32` length prefixes are explicit below.
- JSON fields carrying bytes use standard padded base64.

## Primitives

**Subkeys and AEAD.** Every symmetric encryption uses XAES-256-GCM with a random 24-byte nonce,
encoded as `nonce (24) || ciphertext || tag (16)`, under a per-purpose subkey:

```text
subkey(key, label) = HKDF-SHA512(IKM = key, salt = empty, info = P || label || ENTRY, L = 32)
AAD(label)         = P || label || 0x00 || ENTRY
Enc(key, label, m) = XAES-256-GCM(subkey(key, label), nonce, m, AAD(label))
```

| Label | Key | Plaintext |
| --- | --- | --- |
| `skey/roster-inner` | SKEY | TRUSTEE_MANIFEST |
| `skey/share` | SKEY | SHARE_T (101) |
| `shared/data-key` | SHARED_SECRET | DATA_KEY_SEALED (81) |
| `data/file` | DATA_KEY | FILE (65540) |

SKEY, SHARED_SECRET and DATA_KEY are independent random 32-byte keys. There is no symmetric key for B:
everything only B may open is sealed to B's identity key.

**Sealing** (client only) uses libsignal HPKE, `ECPublicKey.seal(message, info, aad)` /
`ECPrivateKey.open(...)`, which uses a fresh ephemeral key per call. Output: `type (1, = 0x01) || enc (32) ||
ciphertext || tag (16)`, i.e. plaintext + 49 bytes. Lengths are pinned: DATA_KEY_SEALED is exactly 81 bytes,
FILE_METADATA_SEALED 4145, ROSTER_SEALED 52972 and KEY_SHARE_T_SEALED 1395; anything else is rejected.

| Object | `info` | `aad` |
| --- | --- | --- |
| DATA_KEY_SEALED (to B) | `P || "seal/data-key"` | `ENTRY || B ACI || B KEY || A ACI || A KEY` |
| FILE_METADATA_SEALED (to B) | `P || "seal/metadata"` | `ENTRY || B ACI || B KEY || A ACI || A KEY` |
| ROSTER_SEALED (to B) | `P || "seal/roster"` | `ENTRY || B ACI || B KEY || A ACI || A KEY` |
| KEY_SHARE_T_SEALED (to T) | `P || "seal/trustee-package"` | `ENTRY || T ACI || T KEY || A ACI || A KEY` |

**Signatures** (client only) are 64-byte XEdDSA signatures from libsignal (`calculateSignature` /
`verifySignature`) over `P || purpose || 0x00 || fields`. S stores and relays them unverified.

| Purpose | Signer | Fields | Verified by |
| --- | --- | --- | --- |
| `grant` | A | GRANT_DESCRIPTOR | B, before unsealing and after fetching |
| `trustee-sealed` | A | `ENTRY || A ACI || A KEY || T ACI || T KEY || SHA-512(KEY_SHARE_T_SEALED)` | T, before unsealing |
| `trustee-package` | A | TRUSTEE_PACKAGE without its trailing signature | T, before showing instructions |
| `approval` | T | `ENTRY || startedAt (i64) || T ACI || T KEY || SHA-512(SHARE_T_SENC)` | A, against its locally pinned roster |

**Shamir** splits the 32-byte SHARED_SECRET bytewise over GF(2^8) with the AES polynomial `x^8+x^4+x^3+x+1`
(0x11B). For each byte `s`, A picks `M-1` uniformly random coefficients and evaluates
`f(x) = s + a1 x + ... + a(M-1) x^(M-1)` at `x = index`, indices `1..N`. S reconstructs with Lagrange
interpolation at 0. Arithmetic is constant-time (no table lookups indexed by secrets).

## Objects

```text
FILE           = contentLength (u32) || content || zero padding        -- exactly 4 + 65536 bytes
FILE_METADATA  = kind (u8: 1 file, 2 text note)
              || nameLength (u16) || name (UTF-8, <= 255)
              || mimeLength (u16) || mime (ASCII, <= 127)
              || contentLength (u32, <= 65536)
              || messageLength (u16) || message (UTF-8, <= 2048)
              || zero padding                                           -- exactly 4096 bytes
ENCRYPTED_FILE            = Enc(DATA_KEY, "data/file", FILE)                        -- 65580 bytes
FILE_METADATA_SEALED      = Seal(B, FILE_METADATA)                                  -- 4145 bytes
DATA_KEY_SEALED           = Seal(B, DATA_KEY)                                       -- 81 bytes
DATA_KEY_SEALED_SHAREDENC = Enc(SHARED_SECRET, "shared/data-key", DATA_KEY_SEALED)  -- 121 bytes

SHARE_T        = version (1) || share (32) || ENTRY || T ACI || T KEY || index (u8) || M (u8) || N (u8)   -- 101 bytes
SHARE_T_SENC   = Enc(SKEY, "skey/share", SHARE_T)                                 -- 141 bytes

INSTRUCTIONS   = length (u16, <= 1024) || UTF-8 || zero padding           -- exactly 1026 bytes
TRUSTEE_PACKAGE = version (1) || ENTRY || A ACI || A KEY || T ACI || T KEY
               || INSTRUCTIONS || SHARE_T_SENC || signature("trustee-package")   -- 1346 bytes
KEY_SHARE_T_SEALED = Seal(T, TRUSTEE_PACKAGE)                              -- 1395 bytes

SLOT           = T ACI || T KEY || index (u8) || sealedLength (u16 = 1395) || KEY_SHARE_T_SEALED
              || 141 zero bytes (sealed area is 1536 bytes) || signature("trustee-sealed")   -- 1652 bytes
TRUSTEE_MANIFEST = version (1) || ENTRY || M (u8) || N (u8) || 32 x SLOT  -- 52883 bytes
TRUSTEE_MANIFEST_SENC = Enc(SKEY, "skey/roster-inner", TRUSTEE_MANIFEST)  -- 52923 bytes
ROSTER_SEALED  = Seal(B, TRUSTEE_MANIFEST_SENC)                           -- 52972 bytes

GRANT_DESCRIPTOR = version (1) || ENTRY || revision (u32) || A ACI || A KEY || B ACI || B KEY
                || capacity (u8 = 32) || 5 x (length (u32) || SHA-512)    -- 460 bytes
```

`version` is 1 everywhere. In TRUSTEE_MANIFEST the first N slots are used, slot `i` (0-based) has
`index = i + 1`; slots `N..31` are all zero. `1 <= M <= N <= 32`. Trustee ACIs and keys are pairwise
distinct and differ from A's and B's. GRANT_DESCRIPTOR hashes, in order: ROSTER_SEALED,
DATA_KEY_SEALED_SHAREDENC, FILE_METADATA_SEALED, ENCRYPTED_FILE, DATA_KEY_SEALED. It commits to no plaintext
roster data. `revision` is 0 at creation and increases by one with every update (see `share-update`).
The roster is not signed: S cannot verify XEdDSA, B cannot decrypt it, and S authenticates it through
the SKEY AEAD. FILE_METADATA's `contentLength` must equal FILE's; unlike the original draft, B learns the exact
content length from the metadata before release (S and the proxy do not).

A keeps DATA_KEY_SEALED (never DATA_KEY) to build updates, so a later compromise of A's device alone, or
together with S, does not reveal the file: B's identity key is still needed.

## Mandatory client checks

These prevent S from using clients as decryption oracles. Clients never return a generic HPKE or AEAD plaintext.

- **A** only builds a grant for an ENTRY from its own `share-reserve` that is non-zero and that A holds no pin
  for (S could otherwise hand out an ENTRY twice). A persists, before sending `share-create` or `share-update`, the pinned roster of that revision keyed by
  ENTRY: B's ACI/KEY, M, N and for each trustee its ACI, KEY, index and the exact `SHA-512(SHARE_T_SENC)`. Until
  `share-sync` reports the revision, A keeps the previous one too. A verifies relayed approvals against the
  pin of the reported revision (updates end once started) and the entry's single `startedAt`, counting each
  pinned trustee at most once (`approvedAt` is
  informational and unsigned). A release without M valid signatures is *not independently attested*, which
  is not proof that S cheated: S does not verify signatures, so a trustee could have submitted a bad one. A
  revision A never pinned keeps every pin and is flagged, since S could otherwise use it to hide approvals.
- **B**, before opening anything from `share-get`: the owner is a locally trusted contact whose current
  identity key equals the descriptor's A KEY; the `grant` signature verifies; the descriptor's ENTRY is the
  selected entry and its B ACI/KEY are B's own; every returned object matches the descriptor's length and
  hash. Only the explicit start action may send the exact 52923-byte result of opening ROSTER_SEALED. B
  starts with the roster of the newest descriptor it fetched; a `rejected` start means A updated meanwhile,
  so B fetches again. Before opening a fetched DATA_KEY_SEALED, B checks it and ENCRYPTED_FILE against the
  descriptor of the revision it started (fetched again with `share-get`), then that FILE's and
  FILE_METADATA's content lengths agree. Every `share-get` behind a start or fetch must still be the share
  B was shown: the same ENTRY, owner and recipient and the same FILE_METADATA_SEALED, ENCRYPTED_FILE and
  DATA_KEY_SEALED hashes, at the same or a newer revision (S chooses ENTRYs, so it could otherwise answer
  with another trusted contact's grant under the same ENTRY).
- **T**, before opening KEY_SHARE_T_SEALED: the owner is a locally trusted contact with the given current
  key, and the `trustee-sealed` signature verifies over the expected ENTRY, owner, T's own ACI/KEY and the
  exact sealed bytes. After opening: version, ENTRY, owner and T's own ACI/KEY match and the
  `trustee-package` signature verifies, before instructions are shown. Only an explicit approval sends the
  exact signed SHARE_T_SENC field of the request that was shown. T need not know B or verify that B
  initiated recovery.

## What S validates

Create: caller binding (the caller is the descriptor's A), formats, exact lengths and the submitted
ciphertext hashes; it cannot check the signature, roster or SKEY consistency. Update: additionally that
nothing but the roster, SKEY and DATA_KEY_SEALED_SHAREDENC changed (see `share-update`). Start: the SKEY AEAD and the
parsed roster, not byte-for-byte correspondence with the signed ROSTER_SEALED; S learns the roster on
receiving a valid manifest even if the start loses to a concurrent delete. Approve: the decrypted share's
trustee pair equals both the caller's bound identity and the roster slot. A successful reconstruction
authenticates DATA_KEY_SEALED_SHAREDENC, and the result must match the descriptor's DATA_KEY_SEALED hash; S
cannot check the sealed DATA_KEY itself or the file.

## Request authentication

Share request `data` is `{"id": session token, "body"}`, where `body` is base64 (an empty body is `""`). The
session follows the usual rules: an unusable token is `invalid`, a missing entry or a pending lock/wipe returns
the blocking `command` and nothing is performed.

The caller is the session's device (Molly entry), acting as the identity currently bound to it (see "Identity
binding"); without one, the result is `unbound` and nothing is performed. Share requests carry no identity or
proof of their own: the device proved possession of the identity key when binding it, and the session token,
which only travels sealed, authorizes acting as it. Clients only send share requests while the identity last confirmed `bound`
for their session is their current identity, and re-associate first otherwise.

**Identity proof.** `associate` proves the device's Signal identity to S, bound to the exchange it is sealed in:

```text
dh      = X25519(identity private key, transport public key the request is sealed to)
info    = "MihuBot.Molly.Share.Auth.v1" || recipientKeyId (16) || clientEphemeralPublicKey (32)
       || requestNonce (16) || UTF-8 action
authKey = HKDF-SHA512(IKM = dh, salt = empty, info, L = 64)
mac     = HMAC-SHA512(authKey, ACI || KEY)
```

`recipientKeyId`, `clientEphemeralPublicKey` and `requestNonce` are the transport values of the exchange
(`MollyExchangeContext`); the transport authenticates the timestamp separately. Requests sealed to a
discovery key are rejected. An all-zero `dh` is rejected. S compares the decoded 64-byte MAC in constant
time. The MAC proves key possession to S only.

## Identity binding

Each attested Molly entry (device) is bound to at most one Signal identity (ACI, KEY) at a time; the entry
stores the identity and when it was bound. An identity can be bound to several entries at once: linked
Signal devices share the ACI and the identity key pair.

The `associate` request's `data` carries `"identity": {"aci", "identityKey", "mac"}` (base64), where `mac`
is the identity proof MAC above for action `associate`. A request without it, or whose proof
doesn't verify, is `invalid` and changes nothing, not even the nickname. Otherwise the nickname is applied as
usual, and `associate` responses carry `data.identity`:

- `bound`: the entry is now bound to this identity - newly, unchanged, or replacing its previous identity.
- `cooldown`: the entry was bound to a different identity less than 24 hours ago, which stays bound. The
  client retries later.

A wipe unbinds the entry. S only learns that the device possesses the identity key; it cannot
check the ACI-to-key relationship, which peers verify against their own stored identities, so every authorization uses exact
(ACI, KEY) pairs, never the ACI alone. Clients only associate once registered with Signal, and re-associate
whenever their current identity differs from the one last confirmed as `bound` for the session.

**Ownership.** A grant is owned by the device (Molly entry) that created it, whose identity at the time is the
descriptor's A. Only that device lists and deletes it, also after its identity changed; other devices bound
to the same identity don't see it. Recipient and trustee actions use the device's current identity, so grants
to a former identity are no longer accessible. When the owner device's Molly entry is deleted or wiped,
maintenance deletes its grants like `share-delete` does. A device whose app data was cleared registers a new
entry; the grants of its old entry stay live, unmanageable, until the old entry's inactivity expires them (see
"Owner activity"), released ones 30 days after release, or an admin deletes or wipes that entry.

## Actions

Responses with status `ok` carry `data.result`: `ok`, `not-found` (nothing the caller may access, or the
wrong state), `rejected` (failed validation), `limit` (quota) or `unbound`. Statuses
`invalid` (session/format failures) and `command` keep the usual envelopes. In JSON,
`entryId`, ACIs and keys are base64 of their raw bytes; times are Unix seconds and absent times are omitted.

| Action | Body | Caller | Response fields (besides `result`) |
| --- | --- | --- | --- |
| `share-reserve` | empty | A | `entryId` |
| `share-create` | see below | A | - |
| `share-update` | see below | A | - |
| `share-sync` | empty | anyone | `owned`, `received`, `trusteeRequests`, `updatedAt` |
| `share-get` | `ENTRY` | B | `descriptor`, `signature`, `rosterSealed`, `metadataSealed`, `started` |
| `share-start` | `ENTRY || length (u32) || TRUSTEE_MANIFEST_SENC` | B | - |
| `share-approve` | `ENTRY || startedAt (i64) || length (u32) || SHARE_T_SENC || signature("approval")` | T | - |
| `share-fetch` | `ENTRY` | B | `dataKeySealed`, `encryptedFile` |
| `share-delete` | `ENTRY` | A | - |
| `share-dismiss` | `ENTRY` | B | - |

`share-reserve` hands out a fresh random ENTRY for the calling device's next grant, or `limit` if the device
already has 32 owned entries, reservations included. A reservation carries no data, is not listed, and is
dropped if no create used it within one hour. S keeps no record of deleted entries; ENTRYs are 16 random bytes,
so in practice one is never handed out again.

`share-create` body: `version (1) || GRANT_DESCRIPTOR || signature("grant")` followed by five
`length (u32) || bytes` objects: ROSTER_SEALED, DATA_KEY_SEALED_SHAREDENC, FILE_METADATA_SEALED,
ENCRYPTED_FILE, SKEY (32). ENTRY must be an unexpired reservation of the calling device, otherwise the result
is `not-found`. S checks that the caller is the descriptor's A, that B differs from A, that `revision` is 0,
the exact lengths, and the descriptor hashes. S keeps a keyed digest of the entire create body (including
SKEY and the signature): once created, an identical retry returns `ok` until the first update, and anything
else is `rejected`. Deleting or expiring an entry removes it, so a delayed create finds no reservation.

`share-update` body: `version (1) || GRANT_DESCRIPTOR || signature("grant")` followed by three
`length (u32) || bytes` objects: ROSTER_SEALED, DATA_KEY_SEALED_SHAREDENC, SKEY (32). It replaces the
roster of an `active` entry: A splits a fresh SHARED_SECRET over the new trustee list under a fresh SKEY and
re-encrypts its kept DATA_KEY_SEALED. The caller must be the device that created the grant and currently be
bound to the descriptor's A. S checks that `revision` is the stored one plus one, that ENTRY, A, B, the
capacity and the FILE_METADATA_SEALED, ENCRYPTED_FILE and DATA_KEY_SEALED lengths and hashes equal the stored
descriptor's, and the new objects' lengths and hashes; it then replaces descriptor, signature, roster,
DATA_KEY_SEALED_SHAREDENC and SKEY in one transaction, erasing the old SKEY so old rosters can no longer
start (an update reusing the current SKEY is `rejected`). An identical retry of the last accepted update
returns `ok` in any state, since it did take effect; otherwise a started or released entry, or another
device, gets `not-found`; anything else is `rejected`. Updating also keeps the entry alive (see below).
Clients update automatically when a trustee's identity key changed and the new safety number is verified
(otherwise they keep the old key and flag the grant to A), and when A edits the trustees, M or instructions.

`share-sync` lists:

- `owned`: `entryId`, `revision`, `recipientAci`, `recipientIdentityKey`, `state` (`active`, `started`, `released`),
  `createdAt`, `startedAt`, `releasedAt`, `approvals` (`aci`, `identityKey`, `approvedAt`, `signature`), for
  the grants the calling device created (see "Identity binding").
- `received`: `entryId`, `ownerAci`, `ownerIdentityKey`, `state` (`available`, `started`, `released`),
  `createdAt`. No counts, threshold or trustee data.
- `trusteeRequests`: `entryId`, `ownerAci`, `ownerIdentityKey`, `startedAt`, `sealed`, `sealedSignature`,
  for started entries the caller has not yet approved, newest `startedAt` first, at most 64.

`share-get` reports `started` as true once started, including after release.

`share-start` is accepted while `active`: S decrypts the manifest with SKEY, checks ENTRY, policy,
distinctness and zero padding, then atomically moves `active -> started`. Invalid input commits nothing.
Repeating it once started or released returns `ok`.

`share-approve` requires `startedAt` equal to the attempt's start. S decrypts SHARE_T_SENC, checks ENTRY,
that the caller is the slot's trustee, the index and M/N. In one transaction against a live entry, S
deduplicates and records the approval (signature and `SHA-512(SHARE_T_SENC)`), tests the threshold and, at M
approvals, reconstructs SHARED_SECRET, decrypts DATA_KEY_SEALED_SHAREDENC, checks the result against the
descriptor, moves to `released` and erases the
shares. If reconstruction fails, the threshold-crossing approval is rolled back, nothing is released and the
result is `rejected`. Repeating an accepted approval (same share digest and `startedAt`) returns `ok` in
`started` or `released` and is not counted again; a different submission by a trustee that already approved
is `rejected` while `started`. Any other submission in `released`, or on a missing entry, is
`not-found`. Approval signatures are kept for A. Update hints change once per committed change.

`share-fetch` is `released` only. `share-delete` removes the entry in any state, including within the 30
days a released entry is kept; no fetch authorized after the delete commits returns the payload. Its caller
is the device that created the grant.

`share-dismiss` lets B delete an `active` grant, i.e. one it hasn't started, freeing its received quota; in any
other state the result is `not-found`. Clients dismiss grants they don't display (unknown owner, or an owner key
that doesn't match their stored identity) automatically, and offer it for the others.

## State, retention and limits

- One attempt per entry; A ends it by deleting. B can dismiss a grant before starting it. Trustees cannot decline.
- **Owner activity.** Every share request a device makes (clients only make them while unlocked) records its
  activity time. S deletes an `active` or `started` grant like `share-delete` once both its owner device's
  last share request and, if started, its start are more than 14 days old: A has to keep using the app, and a
  started recovery gets 14 days regardless.
- Released entries are deleted 30 days after release. Deleted and expired entries are removed entirely. Grants
  (and reservations) of a deleted or wiped device are deleted (see "Identity binding").
- At most 32 owned entries (including reservations) per device and 256 received entries per identity, of which at
  most 4 may be `active` grants from the same owner device (create returns `limit`); at most 64 trustee requests are listed
  (newest first: requests a trustee ignored longer than the 64 newer ones stop being listed).
- At rest, entry fields are XAES-256-GCM encrypted under
  `HMAC-SHA512(serverKey, P || "at-rest" || ENTRY)[..32]` with `ENTRY || field` as AAD, where `field` is a
  one-byte field ID, followed by the slot as BE16 for per-trustee fields.
  Identities are stored as `HMAC-SHA512(serverKey, P || "party" || ACI || KEY)`.
  `serverKey = HKDF-SHA512(IKM = databaseKey, salt = empty, info = P || "server-key", L = 64)`, never `databaseKey`
  itself, which other Molly code uses to HMAC client-chosen input.

## Update hints

Each identity has an `updatedAt` (Unix milliseconds) that every committed change affecting it raises to
`max(previous + 1, now)`, so it never repeats or goes backwards; it is 0 for an identity nothing happened to
yet. Affected identities: create -> B; update -> B; start -> A, B and every trustee; approve -> A and the approving
trustee; release -> A, B and the trustees that haven't approved; dismiss -> A and B;
delete (including maintenance and expiry) -> B and, if started, the trustees. A is the current identity of the device
that created the grant, if it still has one.

`ping` responses of a device whose entry has a current identity carry that identity's `shareUpdatedAt`
(omitted while unbound). `share-sync` responses carry `updatedAt`, read in the same snapshot as the lists.
Clients remember the `updatedAt` of their last successful sync for their current identity and sync again,
while unlocked, when a ping reports a larger `shareUpdatedAt` or after their identity changed, and at least
hourly, which also keeps their grants from expiring. Nothing happens while locked; clients sync on unlock anyway.

## Padding

Every message of the transport, share actions included, is first padded to its size class: data of at most
1024 bytes gets `paddingLength = 1024 - data`, like pings. Longer share requests and responses get the smallest
`paddingLength` that makes `2 + paddingLength + data` a multiple of 16384 bytes; other longer messages get none.
Then 0-512 random padding bytes (uniform, inclusive) are always added on top, so the total stays within the
16-bit length. Responses are measured after final serialization, including any `transportKey`, and their JSON
escapes nothing that base64 uses, so size classes don't depend on content. Fixed-size objects then give each kind
of message a fixed size class: small requests and results look like pings, while create, start, update, a
successful get or fetch, and sync responses with many entries are larger; the proxy learns which of these
happened and a 16 KiB bucket of the sync response size. Encrypted HTTP request bodies may be up to 256 KiB.
